# Этап 1. Оператор не видит обращения

**Ситуация.** Оператор support_agent должен читать заявки corp.tickets, но система не даёт ему это делать.

### Критерии успешного выполнения
- Оператор читает **всю таблицу** corp.tickets.
- Оператор не может INSERT, UPDATE или DELETE в этой таблице.
- Данные, состав ролей и таблиц не меняются.

Войдите в PostgreSQL и проверьте **\dp corp.tickets**. Для независимой диагностики пригодится запрос:

~~~sql
SELECT has_table_privilege('support_agent','corp.tickets','SELECT');
~~~

Результат true означает наличие указанной привилегии. Для реального теста доступа используйте SET ROLE support_agent и пробный SELECT, затем RESET ROLE.

<details><summary>Подсказка 1 — что искать</summary>
Проверьте права чтения и изменения по отдельности: SELECT не равен UPDATE.
</details>

<details><summary>Подсказка 2 — как читать диагностику</summary>
В выводе \dp буквы r и w обозначают разные полномочия: чтение и изменение.
</details>

<details><summary>Подсказка 3 — пример на другой таблице</summary>
На demo.products команда GRANT SELECT выдаёт чтение, а REVOKE UPDATE отнимает право изменения. Подберите такую же логику для нужной роли и таблицы.
</details>

После исправления нажмите **ПРОВЕРИТЬ**. Система скажет, какое требование осталось невыполненным.
